# 本文・タグ・リンクだけで提案精度を上げる計画（2026-07-20）

オーナーの制約：扱う材料は**本文（タイトルを含む）・タグ・リンク**のみ。
フォルダと作成日時は物理的に必ず存在するため将来検討の余地があるが、frontmatter プロパティは運用によって存在すら不確かで、重み付けの材料としては不安定すぎるため却下。

性能の定義（この会話でオーナーが確定させたもの）は **再現率 / 注意コスト / 設計不備** の三つ。適合率は明示的に優先度が下げられている（誤検出は一瞥のコストしかかからないため）。

再現率は二つに分けて扱う。**候補集合再現率**（関連ノートが候補集合に入るか）と **recall@K**（`maxResults` 件の表示枠に入るか）である。表示件数が有限なので、順位の是正も recall@K には効く。

## 合意した実装順序

### 1. 未解決リンクを独立した仮想リンク先として索引する

効く軸：候補集合再現率。

現在 `buildSnapshot` は `resolvedLinks` だけから `outlinks` を作る（src/cache/metadata.ts:17）。まだ存在しないノートへの `[[X]]` は完全に無視されている。二つのノートが同じ `[[X]]` を書いているという事実は、書き手が同じ概念を明示的に指した一段の完全一致であり、共有アウトリンクと同種の証拠である。

- 解決済みと未解決は別名前空間（`r:path` / `u:X`）とし、df と IDF を独立に計算する。同一実体である保証がないため統合しない。
- 得点は既存の `outlinkWeight` と同じ。割引係数も設定も追加しない。固定の割引は根拠がなく、後から測定して直せなくなる。
- `#heading`、`^block`、alias を除いたリンクパスで比較する。過剰な正規化はしない。
- `excludedLinks` を未解決リンクにも適用する。
- ノート作成に伴う `unresolved → resolved` の移行で二重計上しない。
- **`outlinkCount` に未解決リンクも含めるか**は未決。未解決リンクを大量に持つノートを「リンクの少ない集中したノート」と判定するのは、オーナーの「リンクが増えるほど主張が薄まる」という原則に反する。しかし `outlinkCount` は三つの役割を兼ねている。

  1. 候補の得点を割る MOC 抑制（`outlinkCountPenalty`）
  2. 共有バックリンクの出所特異性の重み
  3. **集中ハブ経由の候補展開ゲート**（`source.outlinkCount > FOCUSED_SOURCE_MAX_OUTLINKS`、src/scoring/index.ts:110-120）

  未解決リンクを足すと 1 と 2 は意図どおり働くが、3 は一部のハブを 20 の閾値の外へ押し出し、**候補展開を止める**。これは項目1自身の再現率目的と逆を向く。「未解決リンクが多いノートは集中していない」と見なすなら意図した結果だが、一つのカウンタが三つの仕事を兼ねているせいで生じる副作用でもある。3 だけ解決済みのみのカウントに分けるか、この締め付けを意図として受け入れるかは、オーナーの判断を要する。

残る偽マージは「別フォルダで別々の将来ノートを意図した同名の `[[X]]`」と、二ノートが共有した同一のタイプミス。後者に IDF は効かない（希少な正しい概念と希少な誤記を区別できない）。どちらも受け入れる。`[[../X]]` と `[[X]]` の食い違いは偽の分割であり、再現率を落とすだけで誤った提案は生まない。

### 2. 親ラン由来を保持し、同一出現の多重投票を解消する

効く軸：設計不備、注意コスト、recall@K。

`addKanjiRun` は漢字連続に対して全体と全 2-gram を出すため、`機械学習` の共有が `機械学習` `機械` `学習` として独立に加算されうる（src/scoring/index.ts:360-365 に抑制はない）。本文経路では standalone・df・top-N・双方の salient 通過というゲートがかかる。タイトル経路（既定 ON）には top-N がない（src/cache/titleTokens.ts:31 は素の `Set<string>` を持つだけ）。ただしタイトルは短く `titleWeight` も 3 なので、絶対量としての影響は本文経路より小さい。効くのは割合で、短いタイトルでは一つの複合語がそのタイトルの寄与のほとんどを占めうる。

守るべき不変条件は「同一の親ランの一出現から派生した全体語と部分語を、独立した複数証拠として加算しない」。

共有集合から単純に部分文字列を消す実装は採らない。本文中に独立して現れた `機械` の証拠まで巻き添えで失うためで、これは再現率とのトレードオフになる。トークナイザーが由来（`derivedFrom`）を残し、親の完全形が双方で共有されている場合にその親由来の部分語だけを追加得点から外す。

### 3. 階層タグの祖先・子孫一致

効く軸：候補集合再現率。

現在タグは文字列完全一致のみ。`#料理/和食` と `#料理/和食/出汁` は共有タグにならない。

- 拾うのは**一方の完全なタグが他方の完全なタグの祖先である場合だけ**。兄弟タグ（`#料理/和食/寿司` と `#料理/和食/出汁`）の仮想共通祖先は最初は拾わない。双方とも別の子タグしか明記していないため、推論が一段弱い。
- 候補展開に使う祖先タグにはハードな df 上限を置く。IDF は候補集合に入った後にしか効かず、候補展開そのものは止められない。
- 一つの枝では最深の共有祖先だけを得点化する（`料理` と `料理/和食` を同時加算しない）。
- 除外タグを祖先・子孫へどう適用するかは仕様化が要る。

### 4. CachedMetadata の位置情報からリンク局所性を得点化する

効く軸：注意コスト、recall@K、設計不備。

`LinkCache extends ReferenceCache extends CacheItem` は `position` を持ち（obsidian.d.ts:3577, 1455）、`sections` `headings` `listItems` にも位置がある。**本文読み取りゼロで、既定のメタデータのみの経路で使える。** プラグインは既に全ノートの `getFileCache` を読みながら、位置情報だけを捨てている。

第三のノート X の中で A へのリンクと B へのリンクが同じ段落・同じ箇条書き群・同じ見出し節にあるなら、「同じノートのどこかに両方ある」より強い証拠である。書き手が関係を認識して並べたことを意味する。

- 同一 paragraph / list group を最強、同一 heading region を次、離れた位置は現行相当とする。
- **候補集合は変えない。** 遠い共引用も、ノート全体が一つの主張なら真の関連でありうる。
- `outlinkCount <= 20` のハード上限は維持する。これは却下済みの「連続的特異性への置き換え」ではなく、上限の内側で証拠の質を区別する別軸である。
- 位置付きの `cache.links` は生のリンク文字列を持つため、`getLinkpath` と `getFirstLinkpathDest` で解決済みパスへ対応づける CPU コストがかかる（I/O はない）。

### 5. 本文 salient を重み付き・支配節付き Map へ変更する

効く軸：注意コスト、recall@K。opt-in 経路のみ。

`rankSalient` は `log(1+TF) × IDF` で順位付けした後、`Set<string>` を返して値を捨てている（src/cache/bodyTokens.ts:265 付近）。得点時に候補側の話題集中度が使えない。

`Map<string, { salience: number; dominantSection: number }>` に変える。保持量は top-N のままで、CLAUDE.md の有界インデックス原則を壊さない。段落単位の完全インデックスは、この近似で明確な不足が見つかるまで作らない。

- 得点に候補側の話題集中度を反映する。同じ三語を共有していても、その三語を中心に書かれた候補を、脇で触れただけの候補より上にする。現在ノート側の広さは強く罰しない非対称な評価にする。
- 局所性は、共有語ごとに `(sectionInA, sectionInB)` の組を作り、同じ組へ集まる共有語の重みを合計する。section 番号はノート間で直接比較できないため、組で扱う。

## 候補集合を広げる変更について

項目1と3は候補集合を広げる。オーナーは一度、候補集合を広げる提案を却下している（`outlinkCount <= 20` のハード上限を連続的な特異性重みへ置き換える案、理由は「弱い証拠で候補を増やす方向だから」）。

区別はこうである。却下された案が広げていたのは、リンク数の多い第三ノートを経由する**二段の間接証拠**だった。項目1は既存の共有アウトリンクと同じ**一段の転置索引照合**であり、項目3は第三ノートを経由しない、明記された二つのタグ間の直接的な包含関係である。どちらもハードな上限を持つ。

ただし、候補集合自体は大きくなりうる。これは隠さない。

## オーナーの判断を要する保留項目

- 本文照合 OFF 時（既定）のタイトルを、既存候補の補助に留めるか完全に無視するか。タイトルは既定経路で唯一の内容信号なので、廃止は候補集合再現率を下げる。`titleWeight` の既定値 3 の妥当性も含む。
- 表示資格ゲート（弱い証拠だけの候補を表示しない）を導入し、再現率と引き換えに注意コストを下げるか。正解ラベルがない以上「弱い候補はすべて誤り」とは言えず、設計不備の修正ではなく製品判断である。
- 階層タグのハード df 上限の具体値。
- 兄弟タグの共通祖先まで照合範囲を広げるか。
- 遠い共引用を将来、候補生成から除外するか。
- `outlinkCount` に未解決リンクを含めるか（上記のとおり、集中ハブ経由の候補展開ゲートを締める副作用がある）。
- 本文の表記ゆれ（`育てる/育てた`、`引っ越し/引越し/引越`、`子ども/子供`）。辞書なしでは偽マージを伴う。harness axis 3 の同定率は現状 5/20（25%）。opt-in 経路なので優先度は最後。

## 議論の過程で撤回された見解

Codex 側：リンク局所性には本文読み取りが必要という認識、表示資格ゲートの早期導入、相対スコア 100 の表示変更、段落単位の完全な本文インデックス、単純な包含語抑制を安全な修正とみなしたこと、タイトル単独候補の廃止を早期実装としたこと。

Claude 側：「一つの複合語共有が常時3票」という誇張、単純な包含語抑制が製品判断不要だという主張、ノート間で section 番号を直接比較できるという前提、階層タグは IDF だけで安全に展開できるという主張（IDF は候補集合に入った後にしか効かない）。
