## 総評

「メタデータ優先・ネットワークなし・常駐プロセスなし」という製品制約が、アーキテクチャ構造(転置インデックスによる候補生成、本文トークンのコーパス/クエリ分離、イベント駆動デバウンス)に正しく翻訳されている。df を再構築でのみ変更するという不変条件、rebuild の一括スワップ、refresh の世代ガードなど、並行性の扱いも丁寧。却下案(時系列フィルタ等)を含む意思決定の文書化は例外的に良い状態。

主要な課題は **「スコアリングが持つシグナルと、候補生成が発見できるシグナルの非対称性」** に集中しており、いずれも既存アーキテクチャの骨格を壊さず修正可能。

## 指摘事項(優先度順)

### 1. 直接リンク(B→A)がスコアされず、バックリンクのみの候補は必ず落ちる 【中〜高】

`scoring/index.ts:75` で `active.backlinks` を候補に追加するが、`computeReasons` / `rawScore` のどこにも「B が A を直接リンクしている」こと自体のシグナルが存在しない(`sharedBacklinks` は A.backlinks ∩ B.backlinks であり、B ∈ A.backlinks は B のスコアに寄与しない)。他の共有シグナルが皆無なら `raw <= 0`(`scoring/index.ts:108`)で除外され、候補追加が実質デッドコード。

「B→A とリンクされているが A→B は未リンク」はリンク提案ツールとして有力な候補のはず。`alreadyLinked` も A→B 方向のみ(`scoring/index.ts:121`)で非対称。

対処の方向: 直接バックリンクをスコアシグナルに加えるか、Obsidian 標準のバックリンクペインとの役割分担として意図的に除外するならその判断を文書化し、デッドな候補追加を整理する。

### 2. 共有バックリンクは「スコアには効くが、候補を発見できない」 【中】

候補生成(`scoring/index.ts:61-86`)はタグ / 共有アウトリンク / バックリンク元 / 本文トークンから引くため、「ハブ C から A と B が共に参照されているだけの B」は候補集合に入らない。`sharedBacklinks` シグナル(重み 4、ソース特異度重み付き — `scoring/index.ts:249-253`)は他シグナルで見つかった候補への加点としてしか働かない。

対処の方向: `active.backlinks` の各ソースのうち **outlinkCount が閾値以下の「焦点の定まったソース」だけ** アウトリンク先を候補展開する。既存の特異度重み(`outlinkCountPenalty` の逆数)と同じ思想で、MOC 経由の候補爆発も抑えられる。

### 3. `hideAlreadyLinked` で results が空になると suggestedTags ごと消える 【中】

`types/index.ts:82-87` は「already-linked なノートはタグプールに残る」と設計意図を明記し、スコアリング層(`scoring/index.ts:126-132`)はその通り `tagPool` をフィルタ前に取る。しかしビュー層 `sidebar.ts:87-91` の `setResults` は `results.length === 0` で `empty` 状態にし、`suggestedTags` を破棄する。全候補がリンク済みのノートを開くと「No related notes found」になり、タグ提案も表示されない — 文書化された設計意図とビューの状態モデルの矛盾。

対処の方向: results と suggestedTags が両方空のときだけ `empty` にする。

### 4. サイドバー再オープン時に「Indexing vault…」で固着する 【中】

ビューの初期状態は loading(`sidebar.ts:24-26`)、`activateView`(`main.ts:371-384`)は refresh を呼ばず、`active-leaf-change` ハンドラは `path === lastRefreshedPath` で refresh をスキップする(`main.ts:106-109`)。ノート X 表示中にサイドバーを閉じ、同じ X のままコマンドで再オープンすると誰も refresh せず、ノートを切り替えるまで loading のまま。鮮度キー(`lastRefreshedPath`)がプラグイングローバルなのに、ビューのライフサイクル(新規インスタンスは初期描画が必要)を考慮していない。

対処の方向: ビューの `onOpen` で refresh を要求するか、鮮度判定にビュー側の描画済み状態を含める。

### 5. 本文トークンの salience が TF を完全に無視している 【中】

`tokenize()` は `Set<string>` を返し(`util/tokenize.ts:78-101`)出現回数が消えるため、`rankSalient`(`cache/bodyTokens.ts:246-265`)は純粋 IDF ランキング。ノート内で 1 回だけ触れたレア語が、主題を表す反復語を top-N(既定 40)から押し出しうる。

対処の方向: `tokenize` を `Map<token, count>` 化し `log(1+TF) × IDF` でランキング。コーパス/クエリ分離・単一スキャン・df 凍結の不変条件すべてと両立する(df 自体は出現有無ベースのままでよい)。実装時の設計判断: 漢字 2-gram 等の派生サブユニットの TF 定義(親ランの出現数を継承するか)。

### 6. salient top-N 同士の交差というリカール上限 【小 — 5 に従属】

マッチには両ノートの salient top-N に共に入る必要があり(クエリ側 `cache/bodyTokens.ts:81-94`、コーパス側は salient のみ索引)、語彙の多い長文ノート同士では共有語が互いの top-40 から漏れる構造的取りこぼしが起きる。索引サイズを有界に保つ意図的トレードオフの側面が強く、上限自体は消せないが、5(TF 導入)で top-N が主題代表的になり実質緩和される。`bodyTokenTopN` 設定も逃げ道。

### 7. `folderWeight` も「スコアには効くが発見できない」 【小・潜在】

同フォルダは `rawScore`(`scoring/index.ts:254-256`)で加点されるが候補生成に経路がなく、folderWeight を上げても「同フォルダなだけのノート」は決して現れない。既定 0 なので潜在的だが、設定を上げたユーザーの期待と挙動が乖離する。1・2 と同型の非対称。

### 8. 起動ごとのフルコーパス再構築(永続化なし) 【将来課題】

毎起動で全 .md を read + トークナイズ(`main.ts:246-255` → `cache/bodyTokens.ts:160-227`)。設定画面自身が 5,000 ノートで ~10–20 秒と明記。現規模では許容範囲だが、モバイル/大規模化で永続化(plugin data に df/salient を保存、mtime で無効化)が選択肢になる。導入するなら「ロード時にスナップショットを丸ごと採用し、閉鎖中に変更があればフル再構築へフォールバック」型にし、df 凍結の不変条件を崩さないこと。

### 9. コーパス再構築に失敗経路がない 【小】

`rebuildAll` のチャンク `Promise.all`(`cache/bodyTokens.ts:170-178`)で 1 ファイルの read が throw すると再構築全体が失敗。`rebuildBodyIndex`(`main.ts:199-230`)に catch がなく unhandled rejection、`bodyRebuildNotify` が立ちっぱなし、初回構築なら `built = false` のまま body マッチングが無通知で不活性化する。回復は手動再構築頼み。

## 軽微な所見(記録のみ)

- **正規化スコア(top=100)は絶対関連度を隠す**: 生スコアの下限は `raw <= 0` のみ。弱い場の消去法の 100 点と強い場の 100 点を区別できない。緩い生スコア閾値でノイズを減らせる。設定画面で非比較性は明示済みなので優先度低。
- **タイトル(ファイル名)がシグナル未使用**: タイトルは純粋メタデータであり、`bodyTokenEnabled` オフのデフォルト体験にも「metadata-first」を破らず追加できる数少ない残りシグナル。将来候補。
- **`suggestTags` のマジックナンバー**(`limit=12`、グローバル df≥3、共起≥2 — `scoring/index.ts:150,176,189`): 公開するなら意図をコメント化した定数に。
- **`refreshNote` と `rebuildAll` の残存レース**: await 中にスワップが挟まると旧 df でランクした salient を新コーパスへ書き込むが、次のイベントで自己修復し統計的に無害。「認識済みの許容」として記録。
- **スコアが共有シグナル数に対し線形無飽和**(`scoring/index.ts:241-261`): 本文トークンを大量共有する長文ペアがメタデータシグナルを圧倒しうる(BM25 的飽和なし)。現規模では実害薄。
- **新規ファイル一括流入時の `backlinksFor` フルスキャン**(`cache/store.ts:38-44`): 1 ファイルごとに O(N) が走る。大量インポート時のみ効く。
