# カタカナ部分語の精度問題と横展開の可否（2026-07-22）

`body-recall-hiragana-decision-2026-07-22.md` でひらがな補修レーンを実装した際、
「カタカナ経路が記録上いちばん弱い」ことが判明した（それが対称コピーを却下した理由）。
本書は、**ひらがなの手法がカタカナに転用できるか**を実測し、できる／できないを切り分けたもの。

**結論を先に：ひらがなで効いた2つの主要手法はどちらも転用できない。**
カタカナの問題は実在し実測できたが、解法は別に立てる必要がある。

## 既知の記録（`tokenizer-eval-2026-07-16.md`）

- カタカナ内部分割 **F1 0.553**（漢字 0.830）— 語種別で最弱
- **ゲートOFF時 precision 0.047**（漢字 0.531）— 生成過剰を `standalone` ゲートが後始末している構造
- `addKatakanaRun`（`src/util/tokenize.ts:160`）は `j <= run.length` の総当たり列挙（上限なし）

## 測定1：問題は実在する（Main vault 1,367ノート）

各ノートについて「そのノート内にフルランとして存在せず、**部分語抽出でしか得られていない**
カタカナトークン」を数えた。

    部分語抽出でしか得られないカタカナトークン: 867種、うち df>=2 が 866種

つまり **866種が実際にノート間の一致を生んでいる**。上位（抽出に依存するノート数順）：

    ライン 74ノート(df=82)   プライ 68(69)   グイン 59(60)   フォル 56(57)
    ワーク 51(53)            ネット 44(55)   ジョン 44(49)   ジャン 43(44)
    ポート 43(49)            セット 42(64)   インタ 40(41)   アウト 38(40)
    リング 37(38)            クライ 37(38)   タイム 36(39)   コミュ 28(29)

親ランとの対応（抜粋）：

    グイン   <- プラグイン      （プラグ|イン を跨ぐ断片）
    フォル   <- フォルダ / デフォルト（後者では デ|フォル|ト の内部）
    フォルト <- デフォルト       （デフォル|ト を跨ぐ断片）
    レート   <- テンプレート     （テンプ|レート を跨ぐ断片）
    マット   <- フォーマット
    リズム   <- アルゴリズム     （アルゴ|リズム。リズムは実在語だが語義が違う）
    ベース   <- データベース     （これは正当）
    グラフ   <- ローカルグラフ   （これは正当）

**`standalone` ゲートが効かない理由**：短いカタカナ断片は、実在する短いカタカナ語と表層が衝突する。
`リズム` は本物の語なので vault のどこかに単独出現し、ゲートを通る。結果 `アルゴリズム` のノートが
音楽の `リズム` のノートと繋がる。ゲートの前提（単独出現＝語）がカタカナでは成立しない。

## 測定2：転用できない手法（重要な否定的発見）

### (a) maxLen 上限 — 転用しても意味が薄い

ひらがなでは O(n²) を固定上限 [3,8] で線形化した。カタカナでは**そもそも問題にならない**：

    カタカナランの長さ: p50=4  p90=7  p99=11  max=22

最長22文字でも部分文字列は240個程度。**O(n²) は実 vault では性能問題ではない**。
記録された弱さ（F1 0.553）は生成「量」ではなく生成「質」の問題であり、maxLen では解けない。

（cap=6/8/10/12 のいずれでも、純粋な派生トークンの df>=2 喪失は 0 だった。
ゲートを通る派生語は必ずどこかでフルランでもあるため、この軸では失うものも得るものも無い。）

### (b) segmenter 由来の辞書 — 転用不可能

ひらがな補修レーンの核心は「segmenter が cross-corpus のどこかで正しく分割した語」を辞書にすること。
**カタカナでは tiny-segmenter がそもそも分割しない**：

    プラグイン    -> ["プラグイン"]
    デフォルト    -> ["デフォルト"]
    アルゴリズム   -> ["アルゴリズム"]
    ローカルグラフ  -> ["ローカルグラフ"]
    リチウムバッテリー-> ["リチウムバッテリー"]

境界の証拠を一切与えないので、辞書源にも被覆分割のオラクルにもならない。

## 性質の違い：これは加算ではなく制限（最重要）

ひらがな補修レーンは**加算レーン**で、baseline 統計を分離したので破壊 0 が構造的に保証できた。
カタカナの精度改善は逆で、**現在出ているトークンを減らす制限**である。したがって：

- **既存ペアを必ず破壊する。** 866種が現に一致を生んでいるので、制限すればその一部は消える。
- 判断基準は「破壊 0」ではなく、**壊れたペアが偽陽性だったかどうか**。人手でのノイズ標本判定が要る。
- `linguistic-eval-2026-07-20.md:351` の警告どおり、「誤りが消える」は言い過ぎで、
  「部分語だけ既知」の recall を失う。recall/precision の交換であり、どちらに転ぶかは測らないと分からない。

## 検討に値する案（いずれも未測定・要実測）

1. **`KATAKANA_SUBWORD_MIN` を 3→4 に上げる**（`tokenize.ts:26`）。上位ノイズ（グイン/プライ/フォル/
   インタ/クライ/コミュ）は大半が3文字。最も安い一手だが、3文字の実在語（ベース/グラフ/ポート）も失う。
2. **`standalone` の証拠しきい値を上げる**：単独出現1回でなく k ノート以上で初めて語と認める。
   偶然1回だけ単独出現した断片を弾ける。`standalone` は現在 Set なのでカウント保持への変更が要る。
3. **接辞位置の制約**：ランの先頭または末尾に接する部分語のみ許す。ただし `グイン`←`プラグイン` は
   末尾接なので、これ単体では今回の最上位ノイズを落とせない（採用するなら他案と併用）。
4. **被覆分割**（`linguistic-eval-2026-07-20.md` が挙げる案）：重なりのある全部分文字列でなく
   非重複の被覆を出す。境界オラクルが要るが、上記(b)のとおり segmenter は使えない。
   外部辞書は `lexicon-decision-2026-07-22.md` で却下済み。**現状オラクルの当てがない。**

## 実測プロトコル（実施必須）

ひらがな作業と同じ枠組みで、案ごとに：

- 追加ペア / **破壊ペア**（今回は破壊が主指標）
- 破壊されたペアの**人手標本判定**（偽陽性が消えたのか、正当な一致を失ったのか）
- 残存する派生専用トークンの df 帯とノイズ標本
- `KATAKANA_SUBWORD_MIN` を変えた場合の失われる実在語の標本
- リビルド時間・索引サイズ（性能は問題になっていないので副次）

比較の baseline は本書と同じ「部分語抽出でしか得られないカタカナトークン 866種（df>=2）」。

## 着手前の注意

- 本書の測定は所有者の単一 vault（1,367ノート）。`single-vault-stats-dont-justify` の方針どおり、
  この数字は**作業の順序を決めるが採否を正当化しない**。
- カタカナのフルランは希少複合語として**それ自体に価値がある**（`リチウムバッテリー`）。
  ひらがなと違い、フルラン非出力は適用してはならない。
- TF二重加算（`サーバー`/`サーバ` が同一正規化）は `03c742d` で修正済み。再導入しないこと。
