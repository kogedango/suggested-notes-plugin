# トークナイザー実測で見つかった問題 (2026-07-16)

> **訂正あり (2026-07-16 後半)。** 初版の数字は採点側の欠陥により**楽観側に偏っていた**。§1 は訂正済み。**§2・§3 の表は未訂正で、再計算が必要**（→ [再計算が必要な箇所](#再計算が必要な箇所)）。定性的な結論はいずれも変わらず、カタカナの問題はむしろ**悪化して**確認された。

測定基準: `src/util/tokenize.ts` のラン分解を、Sudachi A モード（silver reference・文中オフセットで整列）と突き合わせ。極大漢字ラン/カタカナラン（長さ3以上）に限定。ゲートは評価ノートと別のノート群から構築（leakage 排除）。母数 29,924ラン出現（test 651ノートで 16,264）。

ゲート自体は有効（precision **0.201 → 0.835**）。以下は**そのうえで残る問題**。

## 0. 採点範囲について（初版の欠陥）

初版は「**Sudachi が分解しないラン**」を採点から捨てていた。`プラグイン` を `プラグ/イン` に割った失点が一度も数えられず、**カタカナランの 88.9%（14,812/16,653）・漢字ランの 4.3%（565/13,271）が precision の分母から消えていた**。

以下は全ラン採点（誤分割も FP に数える）。recall はいずれの範囲でも不変（gold が空のランは gold 形態素を増やさないため、範囲は precision の分母しか動かさない）。参考に旧範囲の値も併記する。両者は実態を挟み込んでいると読むべき — 全ラン採点は、Sudachi が最も「見解」に近い 88.9% の領域で Sudachi を正解として押し切る側面がある。

|---|---|---|
| ゲートON | P 0.835 / F1 0.773 | P 0.938 / F1 0.814 |

## 1. カタカナ経路の生成過剰 <sub>（訂正済み）</sub>

| | Precision | R(strict) | F1 |
|---|---|---|---|
| 漢字（2-gram） | **0.956** | 0.733 | **0.830** |
| カタカナ（全部分文字列） | **0.480** | 0.651 | **0.553** |

ゲートOFF時の precision は漢字 0.531 に対し **カタカナ 0.047**。`addKatakanaRun` の O(n²) 部分文字列列挙が生成過剰で、standalone ゲートが後始末をしている構造。漢字パスは 2-gram に限定されているぶん最初から出力が筋がよい。

**初版の 0.103 / F1 0.735 は、上記 §0 により実態より良く見えていた。問題は初版が示すより深刻。**

誤出力例: `プライムオンライン→プライ/ライン`、`サプライチェーン→プライ`、`キーバインド→インド`、`バージョン→ジョン`、`セクション→セクシ`

### 修正の当て: `Intl.Segmenter`（初版の記述を差し替え）

初版は「Kuromoji SEARCH の非漢字 長さ7超 閾値」を当てとして挙げたが、**より直接的な選択肢がある**。ECMA-402 の `Intl.Segmenter`（ICU 辞書ベース）は Electron/Chromium に**既に入っており同梱 0 バイト**、オフライン・決定的・ネットワーク不要。同一プロトコルで実測（test 651ノート・全ラン採点）:

| 手法 | 同梱 | 漢字 F1 | カナ F1 | P | R | F1 |
|---|---|---|---|---|---|---|
| 本実装（ゲートON） | 25KB | 0.830 | 0.553 | 0.835 | 0.719 | 0.773 |
| **Intl.Segmenter** | **0 B** | **0.899** | 0.535 | 0.805 | **0.833** | 0.819 |
| kuromoji.js | 39MB | 0.915 | 0.590 | 0.904 | 0.822 | **0.861** |

**漢字は 0 バイトで本実装を +6.9 ポイント上回る**（0.899 vs 0.830）。カタカナはほぼ互角（0.535 vs 0.553）。

ただし `Intl.Segmenter` にも実弱点がある。**ICU 辞書に無い外来語は断片化する**（文脈の有無に関わらず再現）:

```
レコメンドサイト   → レ/コメ/ン/ド/サイト
サイバーセキュリティ → サイ/バー/セキュリティ
```

原子ラン上の誤出力の内訳（「その語を Sudachi 自身がコーパスのどこかで単独形態素として出すか」で二分）は Intl が **43% が断片ゴミ**・57% が境界の見解差、kuromoji が 38%/62%。**辞書系も略語・俗語は砕く**（`マイクラ→クラ`、`ホームラボ→ラボ`）。本実装の同指標は 99.1% が「実在語」だが、standalone ゲートが判別基準とほぼ同じ信号のため**循環しており信用できない**。

`dictionary-free` 制約との関係は §2 の語リスト同梱とは異なる。**バンドルは辞書ゼロのまま**で、辞書はプラットフォームの持ち物。制約の再定義が要るかは判断事項。ICU 版がブラウザ/Electron 版ごとに違うため、**同じ Vault でも環境により結果が動く**点は要検討（索引はローカル再構築なので実害は限定的か）。

## 2. cold start（ゲートはコーパス規模に依存する） <sub>⚠️ 表は未訂正</sub>

> **この表は初版の緩いスコアラー（§0）＋ lenient recall で測られており、再計算が必要。**
> **precision 列は楽観側に偏っている。** recall 列は範囲に不変だが lenient（実装が原理的に出せる gold のみに正解を絞った値）なので、strict ではやや下がる（全体で 0.730 → 0.719 程度）。
> **結論（recall のみコーパス規模に比例・651でも未飽和）は生き残る。**

ゲート構築ノート数のみを変えた測定（test 固定・train からランダム抽出）:

| ノート数 | Precision ⚠️ | R(lenient) ⚠️ | F1 ⚠️ |
|---|---|---|---|
| 25 | 0.966 | 0.316 | 0.476 |
| 100 | 0.963 | 0.435 | 0.600 |
| 400 | 0.945 | 0.663 | 0.779 |
| 651 | 0.938 | 0.730 | 0.821 |

**precision はサイズにほぼ不変、recall のみコーパス規模に比例**し、651ノートでも飽和していない。1,302ノートの Vault ですら、ゲートが必要とする語彙の 67.9%（4,344/6,394）しかカバーできていない。

取りこぼし例: `脆弱性→脆弱`、`気象庁→気象`、`具体的→具体`（実在の語だが、この規模の Vault では単独出現しない）

影響は限定的: body-token 照合は opt-in・既定 OFF であり、既定のメタデータのみの体験はこの問題の外にある。

**修正案は hard constraint と衝突する。** 語リスト同梱（このコーパスが要求する語彙は gzip 24KB 相当）で cold start は潰せるが、語リストは小さな辞書そのものであり、CLAUDE.md の `dictionary-free` 制約に抵触する。採用するなら制約側の再定義が先。（§1 の `Intl.Segmenter` なら同梱 0 バイトでこの衝突を回避しうる）

## この測定が答えていないこと

- **検索/関連ノート提示が実際に良くなるかは未測定。** 測ったのはトークナイザー層のみで、`rankSalient()` の TF-IDF・df<2・df>40%・top-N を通した後の最終品質は見ていない。
- Sudachi A は silver reference であって正解ではない（辞書なし方式を辞書方式の語彙観で採点する循環がある。gold 側にも疑わしい分割がある: `マークダウンファイル→マーク/ダウン/ファイル`）。§0 の全ラン採点は、この循環に最も強く依存する領域で Sudachi を正解として使っている。

- 母数から straddle 2.9% と整列失敗ノート 1.2% を除外。整列失敗ラン（Intl 0.5% / kuromoji 2.9%）は「分解なし」＝recall の損・FP なし として扱った。
