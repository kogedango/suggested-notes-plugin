# 二つのトークナイザー評価の突き合わせ (2026-07-20)

この文書は [tokenizer-eval-2026-07-16.md](tokenizer-eval-2026-07-16.md)（実測）と [linguistic-eval-2026-07-20.md](linguistic-eval-2026-07-20.md)（言語学的評価）を並べ、両者が一致する点、食い違う点、どちらも書いていない点を整理する。
主要な主張は `src/util/tokenize.ts`、`src/cache/titleTokens.ts`、`src/scoring/index.ts` の実装で裏を取った。

## 二つの文書が測っている対象

両者は同じトークナイザーを見ているが、測っている量が違う。

- **07-16**：外在評価。Sudachi A モードを silver reference として、実装のラン分解と突き合わせた実測である。採点範囲は実装が見つけた極大ランの内側に限られる。測定環境は失われており、§2 と §3 の数字は未訂正のまま残っている。
- **07-20**：内在評価。コードと日本語の語構成から直接評価している。採点範囲は文書全体の内容語であり、Vault 実測による該当量の集計が付いている。

この範囲の違いが、以下の食い違いをすべて説明する。

## 強い領域と弱い領域が噛み合っていない

07-20 の「語種による偏り」が引いた地図は、漢語が最も拾いやすく、カタカナは内部の分割精度が低く、和語とひらがな語と送り仮名の多い形が最も弱い、というものである。

この地図の上に、07-16 の目玉である `Intl.Segmenter` の実測を重ねると噛み合わない。

| 領域 | 07-20 の評価 | `Intl.Segmenter` の実測 |
|---|---|---|
| 漢字 | 最も強い | F1 0.830 → **0.899** |
| カタカナ | 弱い | F1 0.553 → 0.535（わずかに悪化） |
| 和語・送り仮名 | 最も弱い | 分母の外（未測定） |

07-16 の推奨は、実装が最も得意な領域を伸ばし、最も苦手な領域については何も言えていない。
したがって「07-16 の提案が 07-20 の指摘を解決する」という読み方は成立しない。

さらに、`Intl.Segmenter` は分割器であって見出し語化を行わない。
引っ越し と 引越し をそれぞれ一語として返すが、両者を同一の型に畳むことはしない。
送り仮名のゆれは分割ではなく同定の問題なので、07-20 の漢字骨格の案は `Intl.Segmenter` を入れても不要にならない。
両者は代替ではなく直列に乗る関係にある。

## 採点範囲という接点

07-20 が 07-16 に対して出した批判は三つあるが、Sudachi A が silver reference である点と、型に対する非重み付き F1 が順位品質と別の問いを測っている点は、07-16 自身が「この測定が答えていないこと」に列挙済みである。
正味で新しいのは採点範囲の指摘だけであり、これは鋭い。

07-16 の測定は実装のラン出力を基準に整列している。
`recall` 0.719 も `Intl.Segmenter` の 0.833 も、ラン内部の指標である。
実装がそもそもランを作れなかった語（和語、ひらがな語、送り仮名の多い形）は分母に入らない。

ここから、どちらの文書にも書かれていない結論が一つ出る。
**07-16 の再構築手順をそのまま実行すると、07-20 が指摘した死角がそのまま再現される。**
「再計算が必要な箇所」に並ぶ五つの必須要件（全ラン採点、pred と gold で同じ長さ下限、表現空間の統一、strict recall、コードポイント基準）は、いずれもラン基準で書かれているからである。

再構築の完全な仕様は、次の四つの軸になる。

1. ラン内部の境界品質（07-16 の五つのスコアラー要件）
2. 文書全体の内容語に対する recall（07-20 の要求。ラン基準では測れない）
3. **表記と活用の変種のあいだの同定率と、誤マージ率**
4. salient と IDF と top-N を通した候補順位の品質（両文書が独立に指摘した downstream 評価）

3 は初稿になかった軸で、Codex との突き合わせで足りないと分かった。
07-20 が指摘した送り仮名のゆれは、境界をどこに引くかの問題ではなく、同じ語を同じ型に畳めるかの問題である。
`addSegmented` は表層形をそのまま発行するので、引っ越し と 引越し は正しく分割されたうえで別の型になる。
参照分割との境界 F1 は、どのコーパスで測っても、この失敗を一度も減点しない。
したがって 1 と 2 をどれだけ整備しても、07-20 が最重要とした欠陥は測定の外に残る。

この軸だけは対比集合で直接測れる。
正例（引っ越し／引越し／引越、打ち合わせ／打合せ、育てる／育てた）が共通の salient token を持つ率と、負例（立ち方／立方、見せ方／見方）が誤って共通 token を持つ率を並べればよい。
コーパスも参照分割も要らないので、四つの軸のうちこれが最も安い。

トークナイザーの差し替えを正当化できるのは、この四軸で測った結果だけである。
intrinsic F1 の 0.773 と 0.819 の差では足りない。

## 制約に対する立ち位置の非対称

07-16 は、最も効く手が `dictionary-free` 制約の再定義を要すると書いている（語リスト同梱で gzip 24KB 相当、あるいはプラットフォーム辞書としての `Intl.Segmenter`）。
07-20 は制約の内側で最適化し、かな漢字の表記ゆれは辞書なしでは解けないものとして、ユーザー設定の同義語リストに逃がす。

ただしこれは正面衝突ではない。
07-20 は `Intl.Segmenter` に反対しているのではなく、言及していない。
そして前節のとおり、安いほうの制約破り（`Intl.Segmenter`）は主要な弱点を直さず、直せるほう（見出し語化する辞書資源）はより大きな制約破りになる。
この対立はきれいには決着しない。

## タイトル索引は両文書の隙間に落ちている

07-16 は「影響は限定的: body-token 照合は opt-in・既定 OFF」と自らの射程を限定しているが、これは過小評価である。
同じトークナイザーが、既定で有効なタイトル索引でも走っている（`titleTokens.ts` の 99 行目と 108 行目）。

しかも 07-16 が測った cold start（`standalone` の被覆はコーパス規模に比例し、651 ノートでも飽和しない）は、本文に対して文字量が二桁小さいタイトル側で最も厳しく出る。
最も痩せたゲートが、最も広く使われる経路に載っている。

## コードで確認した指摘

**カタカナ部分語の TF 二重加算**（`tokenize.ts` の 138 行目から 144 行目）。
`クラウドサーバー` を渡すと、部分文字列 `サーバー` と `サーバ` がどちらも `normalizeKatakana` で `サーバ` に畳まれ、重複除去されないまま 2 回 bump される。
77 行目からのコメントが宣言する「派生した部分単位は親ラン 1 出現につき 1 回だけ bump する」に、実装が反している。

**タイトル側の重複加算**（`scoring/index.ts` の 365 行目）。
`機械学習` を共有する 2 本のノートは、機械学習 と 機械 と 学習 の 3 トークン分が独立に加算される。
タイトル側には top-N がないので、この加算に上限がない。

**07-20 の弱い主張**。
「タイトル側には df ≥ 2 の関門がない」は実質的に空振りである。
2 本のノートが共有した時点で df ≥ 2 は自動的に成立するので、この関門の有無はスコアに影響しない。
タイトル側で効いているのは top-N の不在と `standalone` ゲートの痩せであって、df 関門ではない。

## 作業の順序

これは公開プラグインなので、順序を決めるにあたって二種類の根拠を混ぜない。
**構造的欠陥**（どの Vault でも同じように起きるもの）は、それ自体で修正の理由になる。
**該当量の集計**は所有者の Vault (`Main`、1421 ノート) 一つから取ったものなので、修正の理由ではなく、構造的欠陥どうしの着手順を決めるのにだけ使う。
07-20 の優先順位表は両者が同じ列に並んでいるため、以下で分けて書き直す。

> **この節は 2026-07-20 のコードに対する評価である。**
> 1 と 2 は同日に修正済み（`03c742d`）。以下、修正済みのものは取り消し線で残す。
> 元の 2 本の評価文書は修正前のコードを対象にしており、突き合わせるときは対象コミットを固定すること。固定しないと、評価資料そのものが誤判定の源になる。

### 構造的欠陥（Vault に依らず成立する）

1. ~~派生した部分単位の TF 二重加算~~ **修正済み `03c742d`**。カタカナ側と漢字側の両方で、派生単位を `Set` に集めてから加算するようにした。
2. ~~`TOKEN_RE` の 3 文字下限~~ **修正済み `03c742d`**。大文字ちょうど 2 字の枝を追加した。
3. Unicode の取りこぼし。`[一-龥]` は U+9FA6 以降の統合漢字、CJK 互換漢字（﨑）、拡張漢字（𠮟）を落とす。所有者の Vault では互換漢字 4 件、拡張漢字 0 件だが、**これは修正が不要という意味ではない**。人名と地名を多く扱う Vault では直接効くので、配布先の広がりに応じて上げるべき項目である。同様に ヶ を含む語（一ヶ月）も、どの Vault でも構造的に落ちる。
4. タイトル索引のゲートの痩せ。既定で有効な経路に、最も被覆の薄い `standalone` 集合が載っている。

1 と 2 は、他の何も測らずに直せる。
3 は符号位置基準への統一を伴うので、修正の範囲が `TOKEN_RE` の置換にとどまらない。

### 測ってから決めるもの

漢字骨格、カタカナの被覆分割、`standalone` の閾値化、親子トークンの重複加算の抑制は、いずれも recall と precision の交換である。
どちらに転ぶかは測らないと分からないので、評価基盤の再構築が先に来る。
そのうえ、後で `Intl.Segmenter` に差し替えるなら、これらの作業の一部は捨てることになる。

### 自動では測れないもの

軸 4（候補順位の品質）について、自動的な正解を作ろうとして失敗した記録を残す。
同じ道を二度通らないために書いておく。

試したのは、ある語を共有するノート対が、タグかリンクという独立した関連の証拠も共有している割合を、無作為な対の割合と比べる、という指標である。
参照分割も外部コーパスも要らないので安く見えた。

これは**製品の目的と逆を向いている**。
`CLAUDE.md` は body-token 照合の目的を「タグやリンクを共有していなくても、珍しい語彙を共有するノートを浮かび上がらせること」と定義している。
この指標は、その成功例をそのまま失敗として数える。

「既知の関連すら言い当てない語はノイズだから、否定側のフィルタとしてなら使える」という救済も成立しない。
比率が低いことは少なくとも三通りに読める。
本当にノイズであるか、タグとリンクに現れない独立した発見信号であるか、単に利用者がタグを付けていないだけか。
指標はこの三つを区別しない。

ただし、ここから「評価そのものが不可能」を導くのは誤りである。
一度そう書きかけたので、否定形で残しておく。
**評価に使う情報は、推論時に利用可能である必要がない。**
だから「正解になる信号があるならスコアラーに入れるべきで、問いが再帰する」という論法は成り立たない。
盲検の関連性判定、既存リンクを入力から隠した holdout、提示の受諾、変更で順位が動いた問い合わせだけの A/B は、いずれも再帰しない。

正しい診断はもっと地味である。
**自動で無償に得られる正解ラベルがないだけで、内部評価は可能**。
現状それができていないのは、判定データも操作履歴も保存していないからであって、原理的な障壁があるからではない。
外部妥当性のほうには、性格の違う Vault と利用者が要る。

例外が一つだけある。
**時点 t で無関係だった対が、その後に利用者自身によってリンクされた場合**、それは時点 t のスコアラーには利用できなかった情報なので、再帰しない正例になる。
後から付いたタグ、提示の受諾、リンク挿入も同類である。
ただしリンクされなかった対は負例ではなく未観測であり、利用者の作業順序と露出に強く偏る。
そして現状この履歴は保存されていないので、過去に遡って安く復元することはできない。

結論として、閉クラスの文法語や、実装を既存の不変条件に合わせる修正は測定なしで判断できる。
一方、活用断片のように話題性の有無が争点になる語の採否は、**人間による関連性の判断なしには正当化できない**。
最も安い形は、その語を残した場合と除いた場合で実際に提示が変わった問い合わせだけを対象にした盲検比較である。

### トークナイザーの外側にある欠陥

評価の焦点をトークナイザーに置いていたため、下流で見落としていたものを記録する。
いずれもトークナイザーを差し替えても残る。

**候補生成が二重に recall を切っている。**
本文語が効くのは、active 側の top-N と candidate 側の top-N の**両方**に同じキーが残ったときだけである（`scoring/index.ts` の `addCandidatesByKey`）。
候補生成で落ちたノートは、後段から永久に見えない。
全文検索は文書側を切らないので、これは通常の検索よりはるかに強い制約である。

**top-N の同点に第二キーがない。**
`rankSalient` の `ranked.sort((a, b) => b.score - a.score)` は同点の順序を規定しない。
JavaScript の `sort` は安定なので、実際には Map の反復順、つまり**本文中の初出順**で決まる。
同じ TF と df を持つ語が top-N の境界にあるとき、**文章を並べ替えただけで salient 集合が変わる**。

**表示スコアに下限がない。**
`raw <= 0` だけが足切りで、表示値は `raw / top * 100`。
つまり弱い候補が一件しかなくても、それが 100 と表示される。
希少な断片による誤検出そのものより、弱い結果を強く見せるこの正規化のほうが、製品としては危険である。

**タイトル信号に非対称がある。**
df > 20% のタイトル語は候補展開から除外されるのに、別経路で候補になった相手には同じ語が得点として加算される（`computeReasons` はこのゲートを適用しない）。
候補生成の根拠には弱すぎると判断した語が、順位変更の根拠としては残る。
しかもタイトル専用の除外語設定がない。

### 評価コーパスについて

07-16 は自らの限界として「コーパスが 1 つだけで、しかも本実装のチューニングに使われた Vault」を挙げている。
同じ Vault で基盤を建て直せば、この循環をそのまま引き継ぐ。
とりわけ 07-20 が指摘した和語への偏りは、話題語彙が漢語と外来語に寄った Vault では検出しにくい種類の欠陥であり、単一コーパスでは測れない。

ただしコーパスは、基盤を作り始めることの阻害要因ではない。
阻害するのは**差し替えを決めること**のほうである。
所有者の Vault は、評価器そのものが正しく動くことの確認と、既存利用者に対する退行の検出には使える。
07-16 の時点では外部妥当性を限界として書き添えるのが妥当だったが、いまは「この Vault では見えにくい」欠陥の正体が判明している以上、同じ Vault だけで済ませるのは未知の限界ではなく既知の死角を意図的に残すことになる。

したがって、評価器の構築は所有者の Vault で始めてよい。
そのうえで、漢字骨格やトークナイザーの差し替えの採否は、性格の違う Vault が揃うまで保留する。
