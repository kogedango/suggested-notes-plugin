# 言語学的観点からのトークナイザー評価 (2026-07-20)

この文書は `src/util/tokenize.ts` と `src/data/stopwords.ts` を日本語の語構成と表記体系の側から評価する。
既存の [tokenizer-eval-2026-07-16.md](tokenizer-eval-2026-07-16.md) は Sudachi との一致率を測った実測であり、測る対象の選び方に偏りがある（最終節）。
本文書はその数字に依拠せず、コードから直接評価する。
本文中の分割例はすべて `TOKEN_RE` と `tiny-segmenter` の実出力で確認した。

初稿を Codex に対抗検証させ、確認された誤りと過大な主張を訂正した版である。
訂正の内容は [Codex による検証で訂正した箇所](#codex-による検証で訂正した箇所) にまとめた。

## 設計が正しく捉えていること

先に、この実装が日本語について正しく判断している点を挙げる。
以下の批判はすべて、この土台の上での話である。

**文字種の遷移を第一の分割手がかりにしたこと**は、辞書なしという制約下では最善に近い。
日本語の正書法は内容語の語幹を漢字とカタカナで、活用語尾と機能語をひらがなで書き分ける。
したがって「極大の漢字ラン」はおおむね「内容語または複合語」に一致する。
これは形態素解析の代用ではなく、正書法という別系統の情報を使った独立の手がかりである。

**漢字ランを 2-gram に展開したこと**も定石どおりである。
漢語の複合語は 1 字 1 形態素で構成されるため、2-gram は形態素境界と偶然によく一致する。

**連用形名詞化を活用断片と区別したこと**（`stopwords.ts` が学び、違い、扱いを保護し、読ん、書い、知らを落とす）は、この種の実装が最も間違えやすい区別を正しく踏んでいる。

**カタカナ語末の長音記号を正規化したこと**は、外来語の表記ゆれ対策として最も費用対効果が高い一手である。
ただしこの正規化には実装上の副作用がある（次節）。

## カタカナ部分語の出現数が水増しされる

まず、言語学以前の実装の誤りを一つ挙げる。
`addKatakanaRun` は部分文字列を列挙してから `normalizeKatakana` を通すが、正規化後に同じ形になった別々の部分文字列を重複除去していない。

```
クラウドサーバー（standalone に サーバ がある場合）
→ クラウドサーバ: 1
→ サーバ: 2
```

サーバ と サーバー という二つの部分文字列が、どちらも サーバ に畳まれて 2 回加算される。
`tokenize` のコメントは「派生した部分単位は親ラン 1 出現につき 1 回だけ bump する」と明言しているので、実装がコメントに反している。

TF は `rankSalient` の `log(1 + TF) × IDF` に入るため、長音記号を含むカタカナ語だけが salient 順位で下駄を履く。
語末に長音を持つ外来語は多い（サーバー、ユーザー、フォルダー、メンバー）ので、偏りは系統的である。
局所的で安全な修正であり、最初に直すべきものだと考える。

## 送り仮名のゆれが同一語を分散させる

影響が大きい欠陥は分割ではなく、**同定**の側にある。
同じ語が複数の正書法で書かれたとき、この実装はそれらをほとんど別の型として扱う。

セグメンター有効（既定）での実出力を並べる。

```
引っ越し → 引っ越し
引越し   → 引越し, 引越
引越     → 引越
打ち合わせ → 打ち合わせ
打合せ   → 打合
```

引越し と 引越 は 引越 を共有する。
`TOKEN_RE` の漢字ランがセグメンターの出力とは独立に走るためで、この点で完全に分断されているわけではない。
分断されるのは、送り仮名が最も多い形（引っ越し、打ち合わせ）である。
促音や連用形の送り仮名が入ると漢字ランが 1 字ずつに割れ、漢字トークンが一つも出ない。

送り仮名の付け方は公用文表記と一般表記のあいだで揺れる規範であり、個人の Vault が数年かけて書かれるあいだに書き方が動くのは避けがたい。
df ≥ 2 の関門があるため、影響は取りこぼしにとどまらない。
表記が分散した語はそれぞれの df が下がり、片方が df 1 に落ちれば salient にすら入らない。
表記ゆれは recall を削るだけでなく、統計そのものを薄める。

### 漢字骨格による正規化と、その代償

辞書を使わずに送り仮名のゆれを畳む規則がある。
漢字とひらがなの混じった分割単位から、**ひらがなを落とした漢字だけの列（漢字骨格）**を追加のトークンとして発行する。

```
引っ越し → 引越      引越し → 引越      引越 → 引越
打ち合わせ → 打合    打合せ → 打合
```

ただしこれは安全な同一視の規則ではなく、recall と precision の交換である。
かなを無条件に落とすと、既存の別語と衝突する。

```
見せ方 → 見方      立ち方 → 立方
出し方 → 出方      生き物 → 生物
```

左辺はいずれも tiny-segmenter が一つの混合単位として返すことを確認した。
生き物 と 生物 は語彙的にも近いので害が小さいが、立ち方 と 立方 は無関係である。

実装も見た目ほど単純ではない。
`addSegmented` は `standalone` 収集先を受け取らないので、骨格をそのまま `bump` すると、2 字の骨格はコーパス再構築の第 2 段で「standalone にない漢字 2-gram」と判定されて `isInteriorArtifact` に削除される。
引越 や 打合 という中心的な例がまさにそれに当たる。
骨格を standalone 収集にも通すなどの設計変更が要る。

この規則が及ぶ範囲も区切っておく。
漢字が 1 字しかない語（育てる、見つける、子ども）は骨格が 1 字になり、長さの関門で落ちる。
かな漢字のゆれ（気づき と 気付き、子ども と 子供）も解けない。
これは辞書なしの原理的な限界であり、Sudachi の正規化表記のような語彙資源なしには解けない。

## 語種による偏り

`TOKEN_RE` はひらがなを一切拾わない。
ひらがなが入るのはセグメンター経路だけで、そこでも漢字混じり語と、長さ 3 以上のひらがな語に限られる。
その結果、この実装が拾える語彙は語種によって大きく傾く。

- **漢語**：最もよく拾える。サ変動詞は活用しても漢字部分が動かない（分析する、分析した、分析して がすべて 分析 を出す）ため、活用の問題すら受けない。
- **外来語**：ランとしては確実に拾えるが、内部の分割精度が低い。
- **和語**：最も弱い。育てる、見つける、つながり、まとめ のような語は、漢字が 1 字か 0 字なので `TOKEN_RE` に掛からない。セグメンター経路で拾える場合も、活用形がそのまま型になるため 育てる と 育て が別語として扱われる。

さらに `JA_MIXED_STOPWORDS` は和語動詞をかなり広く落としている（使う、思う、見る、作る、行く、考える、持つ、入る）。
これらの多くは確かに基礎語彙だが、和語がもともと拾いにくいところへ、拾えた分の一部をさらに削っている。

この偏りは製品の性格を決める。
技術や仕事の Vault は話題語彙が漢語と外来語に集中するため、この実装はよく動く。
育児、料理、感情、日記、創作のように話題語彙が和語に寄る Vault では、body-token の効きが構造的に落ちる。
「日本語 Vault 向け」と位置づけるなら、この偏りは日本語一般ではなく特定の文体に向いた設計だという自覚が要る。

### 語末の促音を一律に落とす規則について

`addSegmented` は促音で終わる単位を無条件に捨てる。
コメントは「っ は実際の語末に立たない」と説明するが、これは正確ではない。

```
あっ → あっ      えっ → えっ
やばっ → やばっ  痛っ → 痛っ
```

tiny-segmenter はこれらを語末促音の単位として返す。
会話、日記、創作では切迫した終止や感動詞を表す正規の表記である。
索引語として捨てる判断そのものは妥当（df が高く話題性が低い）だが、根拠は音韻的な不可能性ではなく IR 上の有用性である。
和語に寄った Vault ほど、この規則が落とす量は増える。

## `standalone` は単位性の判定として弱い

`standalone` 集合がやっていることは、術語抽出でいう **unithood**（その部分文字列が独立した語単位かどうか）の判定である。
根拠として「Vault のどこかで単独の文字種ランとして現れるか」を使う。
分布から語単位を推定する発想そのものは正当だが、判定基準としては弱い。

**閾値がない。**
`collectStandaloneInto` は頻度を保持しない `Set` なので、出現 1 回で単位を認める。
誤記が 1 回、見出しの断片が 1 回あるだけで、その単位は Vault 全体にわたって分割を許可し続ける。
salient 側は df ≥ 2 を要求しているのに、単位性の証拠のほうが緩い。

この非対称は不整合だが、閾値 2 を課す判断は自明ではない。
`Set` を頻度付きの `Map` に変える実装が要るうえ（本文とタイトルの両方）、既存の実測は `standalone` の被覆不足がすでに recall を制限していると報告している。
閾値を上げれば precision と引き換えに cold start がさらに悪化する。
測ってから決める話であり、無条件に推奨できるものではない。

**カタカナに対しては証拠の向きが合っていない。**
漢字の場合、2 字ランが単独で立つのは実際に語であるときが多いので、この判定はよく効く。
カタカナは事情が違う。
外来語は長く、自由に複合し、内部に境界標識を持たない。
`addKatakanaRun` はランの部分文字列を長さ 3 以上で総当たりに列挙し、そのうえでゲートに後始末をさせている。
生成側に言語学的な動機がなく、フィルタだけが品質を担っている構造である。

**被覆による分割**は改善の候補になる。
部分文字列の総当たりをやめ、ランが `standalone` の要素だけで隙間なく分割できるときに限って分割を採る。
プライムオンライン は プライム + オンライン で被覆できるが、プライ と ライン は残りを被覆できないので採らない。

ただしこれは無条件の改善ではない。
現行の設計は「残りは未知だが部分語だけ既知」という場合を意図的に拾っており、テストにも書かれている（リチウムバッテリー から バッテリ を取る。リチウム が standalone でなくても取る）。
被覆を要求すると、この recall を失う。
また全ランは必ず `standalone` に収集されるので自明な 1 要素被覆を除外する必要があり、複数の被覆があるときの選択基準も決めなければならない。
誤った `standalone` 要素だけで全体を被覆できてしまえば誤分割は残る。
筋のよい実験候補だが、既存の実測と同じコーパスで、salient 通過後の候補順位まで含めて比較してから採るべきである。

**分岐エントロピー**は、辞書なしで語境界を推定する古典的な基準である[^be]。
境界では次の文字の多様性が跳ね上がるという分布的事実を使う。
決定的でオフライン、辞書ゼロなので制約には適合する。
ただし `standalone` の差し替えではなく別設計である。
現在のコーパス状態は集合しか持たず、左右の文脈頻度、閾値、平滑化、境界競合の解決規則をすべて新たに要する。
小さなコーパスでは分岐の種類自体が観測できないため、cold start が緩やかになるという保証もない。

[^be]: Harris の境界仮説に由来し、accessor variety や branching entropy として教師なし形態素分割で標準的に使われる基準。

**規模依存**は受け入れられた劣化として文書化されているが、影響はもう少し広い。
`standalone` の質はコーパス規模の関数なので、同じノートでも 200 ノートの Vault と 2000 ノートの Vault で**型の集合そのものが変わる**。
遅れるのは df と重みだけではなく、語彙の同定である。

## 複合語の部分単位が重複して加算される

機械学習基盤 が発行されるとき、`standalone` を通った 2-gram（機械、学習、基盤 など）も同時に発行される。
両方のノートの salient 集合に親と子が残れば、スコアはそれぞれ独立に加算される。

IDF はトークンごとに独立に計算されるが、上位語と部分語は独立な事象ではない。
片方が出れば他方も必ず出る。
それを独立項として和を取っているので、**長い複合語を共有するノートが、単純語を一つ共有するノートに対して過大評価される**方向に働く。
outlink 数には MOC 支配を抑える罰則があるのに、複合語の長さには対応する補正がない。

ただし「1 回の出現で必ず 4 件分」ではない。
部分語は `standalone` を通り、df ≥ 2 と df 上限と top-N を通り、双方の salient に残ってはじめて加算される。
機構は確実に存在するが、順位にどれだけの偏りを生むかは候補順位での測定なしには確定しない。

同じ問題は**タイトル信号にもある**。
`TitleTokenIndex` も全ランと部分語を発行し、`scoring/index.ts` は各 title token を独立に加算する。
しかもタイトル側には top-N も df ≥ 2 の関門もない。
タイトル信号は既定で有効なので、既定体験に効くのはこちらである。

補正のうち、部分単位の寄与を親ランが生んだ単位数で割る方式は「どの親ランから派生したか」という由来の情報を要し、現在の `Map<string, number>` と `Set<string>` はそれを保持していない。
一方、最長一致優先は由来を持たなくても実装できる。
共有トークンの集合を得た時点で、その集合内の他のトークンの部分文字列になっているものを抑制すればよい。
共有トークン数は小さいので、集合内の総当たりで済む。
設計変更を伴わないので、まずこの形で実害を測るのが順序として妥当である。

## 文字クラスの取りこぼし

`TOKEN_RE` の実出力で確認した抜けを挙げる。

**2 文字の英字略語が拾えない。**
`[A-Za-z][A-Za-z0-9_\-]{2,}` は最低 3 文字を要求する。
AI、ML、UI、UX、DB、OS、PC、VR、AR、QA が一つも拾えない。

```
"AIとMLの話"   → []
"UI/UXとDB設計" → ["設計"]
```

技術系の Vault では、これらは IDF が高く話題性も高い、まさに拾いたい語である。
ただし長さ条件を一律に緩めるのは安全ではない。
現在の `ASCII_STOPWORDS` は 3 文字以上を前提に組まれており、in、of、to、is、on、at、by といった 2 文字機能語を持たない。
**大文字 2 字に限って**選択肢を足すのが現実的な範囲である。

同じ欠落クラスに、先頭が数字の語（3D、5G）と 1 文字の言語名（R、C、Go）がある。
数字始まりを許すと日付や連番を大量に拾うので、こちらは単純な緩和では解けない。

**ヶ を含む語が落ちる。**
一ヶ月 は 一（漢字 1 字）、ヶ（カタカナ 1 字）、月（漢字 1 字）に割れ、どのランも長さ 2 に届かない。
セグメンターは 一ヶ月 を正しく一語として出すが、`addSegmented` は漢字とひらがなの共起を要求するため、ここでも落ちる。
三ヶ月、一ヶ所も同様である。

**互換漢字と拡張漢字が漏れる。**
`[一-龥]` は U+4E00–U+9FA5 であり、U+9FA6 以降の統合漢字が入らない。
CJK 互換漢字（﨑 U+FA11 など）と、サロゲートペアの拡張漢字（𠮟）も対象外である。

```
"髙橋と﨑山" → ["髙橋"]
```

髙（U+9AD9）は範囲内だが 﨑 は落ちる。
人名や地名を多く扱う Vault では効いてくる。

この修正は文字クラスの置換だけでは済まない。
`\p{Script=Han}` は 々 を含む一方、康熙部首（⼀ U+2F00）や CJK 部首補助（⺀ U+2E80）まで拾ってしまう。
過捕捉を避けるなら `[\p{Unified_Ideograph}々〇]` のほうが目的に近い（`\p{Unified_Ideograph}` は 々 を含まないので明示が要る）。
さらに `addKanjiRun` の `run.length` と `slice(i, i + 2)` は UTF-16 の符号単位基準なので、拡張漢字を範囲に入れると 𠮟責 が 𠮟 と壊れたサロゲート片に割れる。
`isInteriorArtifact` の長さ判定も含め、符号位置基準に揃える必要がある。

## タイトル索引はゲートが痩せている

`TitleTokenIndex` は `standalone` 集合をタイトルだけから構築する。
タイトルは 1 本あたり十数文字で、本文コーパスに対して文字量にして二桁小さい。
`standalone` の被覆はコーパス規模に比例するので、タイトル側のゲートは本文側よりはるかに疎になる。
「日本語入門」から 日本 を取り出すには、日本 が**タイトルとして単独で**どこかに存在しなければならない。

しかもタイトル信号は既定で有効であり、body-token と違って無効化する設定がない。
最も痩せたゲートが、最も広く使われる経路に載っている。

素朴な対策として本文の `standalone` との和集合が思いつくが、これは製品の制約と衝突する。
本文読み取りは opt-in の例外として切ってあるのに、既定有効のタイトル索引がその成果物に依存すると、metadata-first の境界が崩れる。
body index の有無でタイトルの型集合が変わり、両索引のライフサイクル依存も戻ってくる。
タイトル改善は、本文コーパスを借りる話ではなく、タイトル専用のトークナイザー設計として立てるべきである。

なお、タイトルは常に `segment=false` で処理される。
したがってセグメンターの混合単位を前提にする漢字骨格の案は、そのままでは既定体験のタイトルには一切効かない。
送り仮名のゆれの指摘は、body-token を有効にした利用者に限った話である。

## 既存の実測評価について

[tokenizer-eval-2026-07-16.md](tokenizer-eval-2026-07-16.md) は、測定手続きの欠陥を自ら訂正しており、その点は信頼できる。
ただし測る対象の選び方に、注意すべき点がある。

**採点範囲が、この実装が最も弱い領域を含んでいない。**
測定は「極大漢字ラン、カタカナラン（長さ 3 以上）に限定」されている。
つまり、トークナイザーがすでに見つけたランの内側だけで正解と突き合わせている。
本文書が指摘した和語、ひらがな語、送り仮名のゆれは、そもそも分母に入らない。
文書全体の内容語に対する recall は、この測定からは何も言えない。
報告値 0.719 はそれ自体が限定範囲の指標であり、外挿する母数も正解データも残っていないので、真の値がどれだけ低いかを推定することもできない。

**正解の単位が課題に合っていない。**
Sudachi A は短単位であり、注釈の一貫性のために設計された形態論的単位である。
索引に適した単位は最短形態素でも最長複合語でもない。
Sudachi 自身が A/B/C の三モードを持ち、Lucene の Kuromoji に SEARCH モードがあるのは、まさにその理由による。
A モードを正解に置くと、機械学習を全体としても部分としても保持するという、この実装が意図してやっている振る舞いが減点される。
もっとも、この点は既存文書自身が silver reference として列挙済みであり、本文書が新しい反証を出しているわけではない。
同一の参照に対する境界挙動の**相対比較**としては、依然として有用な指標である。

**型に対する P/R/F1 は、順位品質と別の問いを測っている。**
このシステムは順位付け器である。
df 2 で IDF の高い誤トークンは致命的だが、df 400 の誤トークンはほぼ無害である。
すべての型を等価に数える F1 は、スコアリング層が意図的に等価に扱っていない量を測っている。

ただしこれは置き換えではなく補完の関係である。
salient に入ったトークンだけを採点すると、そもそも生成されなかった正解語が分母から消え、recall の欠落が見えなくなる。
必要なのは intrinsic な F1 を捨てることではなく、**salient と IDF と順位変化まで通した downstream 評価を足すこと**である。
トークナイザーを差し替える根拠としては、intrinsic F1 の 0.773 と 0.819 の差だけでは足りない。

## 優先順位

指摘の当てはまる量を Vault (`Main`、1421 ノート) で数えたうえで並べる。
測定は NFKC 後の本文に対する単純な出現数であり、markdown 除去は通していない。

| 項目 | 該当量 | 費用 | リスク |
|---|---|---|---|
| カタカナ TF 重複 | 長音終わりの長いカタカナ列 1,351 件 / 362 ノート (25%) | 数行 | ほぼ無し |
| 大文字 2 字略語 | 3,236 件 / 479 ノート (34%)。AI だけで 1,304 件 | 数行＋stopword 追加 | 低 |
| 親子トークン重複加算 | 未測定 | 小（下記の抑制案なら） | 低 |
| カタカナ被覆分割 | 未測定 | 中（評価基盤の再構築込み） | 中 |
| 漢字骨格 | 未測定 | 中 | 中（偽マージ） |
| `standalone` 閾値化 | 未測定 | 小〜中 | 効果の符号が不明 |
| Unicode 拡張漢字 | 互換漢字 4 件 / 3 ノート。拡張漢字と U+9FA6 以降は 0 件 | 中 | 中（型集合が全面的に動く） |
| ヶ を含む語 | 3 件 | 小 | 低 |

**今すぐ直す価値があるもの。**
カタカナの TF 重複は、当てはまる語形が 4 ノートに 1 本の割合で現れ、修正は数行で、コメントが宣言している仕様に実装を合わせるだけである。
大文字 2 字略語は、AI が単独で 1,304 件あり、これが一つも索引に入っていない。
ただし上位には MM、DD、OK、AA、AB のような日付書式や表の断片も混じるので、大文字に限定したうえで stopword を数語足す必要がある。

**測ってから決めるもの。**
親子トークンの重複加算は、共有トークン集合の中で他の共有トークンの部分文字列になっているものを抑制する形なら、由来情報なしに試せる。
まずこの形で候補順位がどう動くかを見る。
カタカナの被覆分割、漢字骨格、`standalone` の閾値化は、いずれも recall と precision の交換であり、どちらに転ぶかは測らないと分からない。
既存の評価基盤は失われているので、この三つを検討するなら基盤の再構築が前提になる。

**この Vault では優先度が低いもの。**
Unicode の拡張漢字対応は、互換漢字が 4 件あるだけで、拡張漢字も U+9FA6 以降も 0 件だった。
指摘そのものは正しいが、この Vault では取り分がない。
人名や地名を多く扱う Vault に配布する段階で考えればよい。
ヶ を含む語も 3 件で、同様に急がない。

**後続の課題。**
分岐エントロピーは制約には適合するが `standalone` の差し替えではなく別設計であり、統計と閾値と再構築コストを含む。

**採らないもの。**
タイトルへの本文 `standalone` 併用は metadata-first の境界を崩す。
タイトル専用トークナイザーとして設計し直すのが筋である。

かな漢字の表記ゆれ（子ども と 子供）は、辞書なしでは解けない。
制約と引き換えに失っているものとして明示し、必要なら `excludedBodyTokens` と同じ性格のユーザー設定（同義語リスト）を逃げ道に置くのが、制約と両立する形になる。

## Codex による検証で訂正した箇所

初稿から次の主張を訂正した。
いずれも Codex の指摘を実機で再現して確認した。

- 送り仮名の三表記が「共有語彙を一つも持たない」は誤り。引越し と 引越 は漢字ラン経由で 引越 を共有する。分断されるのは送り仮名が最も多い形（引っ越し）である。
- 漢字骨格が「既存の経路にそのまま入る」は誤り。`isInteriorArtifact` に削除される。また 立ち方 → 立方 のような偽マージを伴う。
- `standalone` の df ≥ 2 化が「一行」は誤り。頻度を保持しない `Set` の構造変更が要り、cold start を悪化させうる。
- カタカナの被覆分割で誤りが「消える」は言い過ぎ。既存テストが要求する「部分語だけ既知」の recall を失う。
- `\p{Script=Han}` で「一括で解決」は言い過ぎ。部首ブロックを過捕捉し、符号単位ベースの走査は拡張漢字で壊れる。
- 語末促音を「音韻的事実」で正当化したのは不正確。あっ、痛っ、やばっ は正規の表記である。落とす根拠は IR 上の有用性に置き直した。
- 「真の recall は 0.719 よりかなり低い」は根拠がない。限定範囲の指標から全体を推定することはできない。
- 既存評価への批判のうち、Sudachi A と非重み付き F1 の点は、既存文書自身が列挙済みの限界であり、否定ではなく downstream 評価の追加根拠として位置づけ直した。
- カタカナ部分語の TF 水増しと、タイトル信号側の重複加算は、初稿の見落としとして追加した。
